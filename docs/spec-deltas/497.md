## §12.4 — CLARIFIED (reconciliation is scoped to assistant candidates, never a discovery side effect)

**Section clarified**: §12.4 ("WHEN the engine restarts THE SYSTEM SHALL reconcile the
queue: tasks with an external_job_id are re-polled against the remote system before any
resubmission; unreconcilable tasks become orphaned"). The text says "the queue" without
saying which repos own one — silent under the exact ambiguity AST-067's retro-review
(#485) caught: `tasks.py`'s `_reconcile_all` (startup) and `_reconcile_live_all`
(AST-070's periodic twin) both iterate every root `repos_getter()` yields, and
`repos_getter` (engine.py's `self._repos_getter`) enumerates every `.neural-network`-
anchored repo, not just assistant candidates — the same live `{name: root}` pairs
`capability_index.run_worker` walks. Both sweeps opened a connection unconditionally for
every yielded root, and `_open_conn`'s `os.makedirs(.claude/assistant/)` + `CREATE TABLE
IF NOT EXISTS` is a side effect of merely OPENING one — so a repo with no assistant
config at all, and even a real assistant candidate that had never queued a task, grew an
empty `tasks.sqlite` just from being anchored and present in `repos_getter()`'s list.
Live evidence: 8 anchored repos on the reporting machine had this empty db; in 4 of them
`.claude/assistant/` was not gitignored, exposing §17.8's "tasks are never committed to
git" invariant.

**Contract now**: both sweeps SHALL open a connection for a root only when that root is
BOTH (a) an assistant candidate (`discovery.classify_repo(root).kind == "candidate"` —
the same classifier `capability_index.run_worker` already gates its own `repos_getter()`
walk with, per this codebase's "exactly one classification code path" rule) AND (b)
already has a `tasks.sqlite` on disk (i.e., has queued at least one task before). A
non-candidate root is never touched. A fresh candidate with nothing queued yet is left
alone too — there is nothing to reconcile, so opening a connection for it would recreate
the identical bug for a legitimate assistant repo instead of a non-assistant one. Once a
root's connection is open (whether via reconciliation or via the normal
enqueue/`_process_create` worker path), it stays open and reconciles normally for the
rest of the process's life — this gate governs only the decision to open a FRESH
connection, never an already-legitimate one. `tasks.py`'s `_is_reconcile_candidate(root)`
is the single choke point both sweeps call.

**Unaffected**: the normal enqueue/worker path (`enqueue` -> `_process_create` ->
`_open_conn`) for a root actively receiving a task is unchanged — it legitimately creates
`tasks.sqlite` on first use, exactly as before. §12.3's queue/state-machine contract and
§12.4's actual re-poll/orphan logic per row are unchanged; this delta narrows only WHICH
roots reconciliation ever opens a connection for, never what it does once opened.
