## §17 Invariants — ADDED (§17.11, issue #345, OWNER threat-model directive)

**Section changed**: §17 (Invariants) gains a new numbered invariant.

**Added text** (paste-ready, appended after invariant 10):

> 11. A task executor never persists an `artifact_path` it did not itself construct.
>     Artifact paths are built engine-side from the task's own id; an executor SHALL
>     NEVER accept, parse, or otherwise adopt a path (or path-shaped field) supplied by
>     a dispatched job's own output, response, or anything else crossing the process
>     boundary.

**Why this is a spec-level addition, not just an implementation note**: the OWNER's
directive on issue #345 is a hard, cross-cutting security requirement that will bind
every FUTURE task-kind executor this repo ever registers (E7's `comfyui-render`
included, per docs/design/ast-E6.md's "Out of scope for this epic" note that E7 builds
on E6's contract) — not something local to `harness.py`. §12.2/§12.3 already establish
that `artifact_path` is interpreted as relative-to-the-artifacts-root and resolved
through `artifacts.resolve()`'s containment check, but neither section states WHO is
trusted to produce that value in the first place. This closes that gap at the
invariant level, the same way invariants 2/3/5 already state cross-cutting subprocess/
argv/write-safety rules rather than leaving them as one task's private implementation
detail.

## §9.4 / §12.3 / §12.4 — concretized (AST-070, no normative text change)

§9.4 ("Harness jobs... own sandbox posture, full tracing") and §12.3/§12.4 (the task
state machine and restart reconciliation) already describe the required BEHAVIOR;
AST-070's job is filling in the concrete mechanics those sections deliberately left to
the implementing task (mirroring how AST-066/067 left `executors`/`resolvers` as
generic, empty seams — see tasks.py's own module docstring). No spec text changes here;
this section records the decisions so a later task extending harness jobs (or adding a
second dispatched-agentic-run kind) has one place to read them.

### Task kind

`harness.KIND = "harness-job"`, registered into `engine.py`'s `start()` — the `tasks`
worker slot's `executors`/`resolvers` kwargs now carry
`{"harness-job": harness.run_harness_job}` / `{"harness-job": harness.resolve_harness_job}`
alongside the (still otherwise empty) generic seams AST-066/067 built. This is the
FIRST real task kind riding that machinery; every other kind still has no
executor/resolver, so an unrelated enqueued kind still fails/orphans specifically and
immediately, unchanged.

### Own sandbox posture (§9.4), distinct from a turn (§8.4)

A turn (§8.4) disables tool use outright (`claude --tools ""` / codex `-s read-only`
with no tool-disable flag at all — a documented gap `codex.py` already flags). A
harness job is, per §9.4's own wording, a "full agentic run" — tool use is EXPECTED,
not disabled, but bounded to a fresh, isolated, per-job working directory the
dispatched process can never escape:

- **codex**: `-s workspace-write` (not the turn's `read-only`) + `-C <isolated dir>` +
  every other turn-isolation flag verbatim (`--ignore-user-config`, `--ignore-rules`,
  `--ephemeral`, `--skip-git-repo-check`, an isolated `CODEX_HOME` carrying only a copy
  of `auth.json` — reusing `codex._isolated_codex_home()`, the already-researched
  isolation this codebase already vetted for turns, not re-derived).
- **claude**: `--safe-mode` (no CLAUDE.md/plugins/hooks/MCP, same as a turn) but WITHOUT
  `--tools ""` — full tool surface, auto-approved via `--permission-mode acceptEdits`
  (headless has no interactive prompt), bounded to an isolated `cwd`. No
  `CLAUDE_CONFIG_DIR` override, same documented reasoning `claude.py`'s own module
  docstring already gives for turns (overriding it breaks real auth with no isolation
  benefit `--safe-mode` doesn't already provide).

Both providers spawn via `subprocess.Popen` (argv-array, `shell=False`), not
`adapters.invoke_cli` (`subprocess.run`) — a harness job needs the child's pid BEFORE
it exits (to persist `external_job_id` promptly, see below) and needs to poll for
progress instead of blocking once; the poll loop enforces the SAME mandatory-timeout
invariant `invoke_cli` enforces (kills the child, never an unbounded wait), so this is
the same subprocess-discipline family, not a second, laxer one.

### `external_job_id` semantics (§12.4)

A locally-spawned harness run has no remote system to poll. `external_job_id` is
`"{task_id}:{pid}"` (`harness._encode_external_job_id`/`_decode_external_job_id`) —
task-id-prefixed so a restart-time resolver, which per `tasks.py`'s contract receives
only `(external_job_id, payload)` (never `task_id` directly), can still recover the
task's own state-dir key. The durable side of "re-poll... before any resubmission"
(§12.4) is an atomically-written (temp file + `os.replace`) completion marker,
`.claude/assistant/tasks/<task_id>/result.json`, written by the executor the instant
the dispatched process exits. `resolve_harness_job` answers:

- marker present, `state: completed`/`failed` → that recorded outcome wins outright
  (never re-derived from a live pid check, even if the pid happens to still resolve to
  SOME process — a later, unrelated process reusing the pid must never override a
  genuine completion record). **Round-1 review BLOCKER fix (issue #345)**: a completed
  marker's `artifact_path` is REBUILT from the decoded `task_id`
  (`_artifact_rel_path(task_id)`), never read out of the marker file itself — see the
  "Artifact-path construction rule" section below for why a stored value is untrusted
  the instant it crosses a restart boundary, even one this same module wrote. `result`
  IS passed through from the marker as-is — this is a materially different trust
  question than a filesystem path: `result` is opaque, rendered text the artifact panel
  displays (never interpreted as a path or executed), so there is no equivalent
  substitution/traversal primitive hiding in it the way there is in an unexamined path
  string. It is still, in the same sense as any executor-boundary value, not something
  the engine independently verified — a hostile or buggy executor could put misleading
  TEXT there, same as it always could for a live (non-reconciled) completion's `result`
  too; this is a pre-existing, general property of `result` (Sec12.3's data model),
  not a new gap this task introduces.
- no usable marker, pid alive (`os.kill(pid, 0)`) → `in_progress` (never resubmitted).
  **Round-1 review MAJOR fix (issue #345)**: this outcome is no longer a dead end. The
  one-time startup sweep (`_reconcile_all`, AST-067) is not the only thing that ever
  re-polls such a row — `tasks.run_worker`'s drain loop now ALSO runs a periodic
  `_reconcile_live_all` pass (default every `DEFAULT_LIVE_RECONCILE_INTERVAL_SECONDS` =
  30s, configurable via `run_worker(..., live_reconcile_interval=...)`), reusing
  `_reconcile_row`'s exact per-outcome logic against a narrower row set: only
  `started`/`progress` rows that already carry an `external_job_id` (a bare `queued`
  row is deliberately excluded from the PERIODIC pass — unlike the one-time startup
  sweep, a `queued` row found mid-loop can be a legitimate, imminent item already
  sitting in the in-memory queue about to be drained normally, and treating it as an
  orphan would be a correctness bug). This is what actually makes "conversation
  resumable mid-job" (§9.4, AST-070's own AC) true across a restart: a job that was
  still running when the engine came back up is checked again, and again, until its
  marker lands — never resubmitted, same trace-event shape as any other reconciliation.
- no usable marker, pid dead → `not_found` (this locally-spawned job's honest
  equivalent of "the remote system has no record of it" — the process is gone and left
  no trace).
- a malformed/undecodable `external_job_id`, or a payload missing `root` → `not_found`
  as well (nothing to look up); this resolver never raises for a routine
  "can't-identify-this-job" case, only for a genuinely unexpected internal failure.
  **Round-1 review MINOR (d) fix (issue #345)**: "malformed" now includes a decoded
  task id that fails `_TASK_ID_RE` (`^[A-Za-z0-9_-]+$`) or a pid that is not a positive
  integer — an `external_job_id` is untrusted the instant it crosses a restart, and it
  is used to build an on-disk path (`_job_state_dir`/`_marker_path`); a `/` or `..`
  inside a decoded task id would otherwise be a real path-traversal primitive, and
  pid 0 is meaningless (`os.kill(0, 0)` targets the whole process group, not one job).

**Known, documented gap**: raw pid liveness can theoretically false-positive if the OS
recycles a pid in the narrow window between an engine crash/kill and the next
reconciliation pass (startup OR periodic), before a completion marker would have
existed. No `/proc` cmdline-style cross-check is attempted (not portably available on
macOS). This does not undermine §12.4's actual invariant (never resubmit) — a false
`in_progress` degrades to "still shows as running," never to a duplicate submission.

### Artifact-path construction rule (§17.11 above)

`harness._artifact_rel_path(task_id) = f"{task_id}.log"` is the ONLY function in
`harness.py` that produces an `artifact_path` value, called exactly once per outcome
site, a pure function of the task's own id. The dispatched job's captured combined
stdout+stderr is copied verbatim into that engine-chosen file (`_publish_artifact`) —
its CONTENT is whatever the harness CLI produced (that is the point: it is the run's
transcript), but its LOCATION and NAME are never negotiable.

Two DISTINCT smuggling surfaces are covered, not one (round-1 review, issue #345 —
the original delta scoped this to stdout only, which was too narrow):

1. **The dispatched job's own stdout/stderr/workdir files.** No code path in
   `run_harness_job` reads a "path"/"artifact_path"-shaped key out of any of these.
   Covered by a hostile-stdout test (`section-assistant-tasks.sh`, "SECURITY (OWNER
   threat-model directive...)" section): a fake harness binary emits stdout containing
   a crafted `{"artifact_path": "../../../../etc/passwd"}` line; the resulting task
   row's `artifact_path` is still the engine-constructed `<task_id>.log`.
2. **A stored completion marker, at restart-reconciliation time (BLOCKER, round-1
   review).** The reviewer demonstrated a cross-task substitution: a marker file
   naming a DIFFERENT real task's artifact (e.g. `secret-other-task.log` — still
   safely INSIDE the artifacts root, so `artifacts.resolve()`'s escape-only containment
   check would never catch it, since that check only blocks paths that leave the
   root, not same-root substitution) would have been served verbatim by
   `/assistant/artifact/<task_id>` under the original design, which trusted
   `marker.get("artifact_path")`. Fixed by making `resolve_harness_job` NEVER read
   `artifact_path` out of a marker at all — a completed outcome's path is always
   `_artifact_rel_path(task_id)`, rebuilt fresh from the id the resolver itself just
   decoded from `external_job_id`. `run_harness_job` no longer even WRITES
   `artifact_path` into a marker — a marker carries only `state`/`error`/`result`.
   Covered by a dedicated hostile-marker test (`section-assistant-tasks.sh`, "SECURITY
   (round-1 review BLOCKER...)" section) with both a same-root foreign-file value and a
   traversal-shaped value, both ignored.

Both cases reduce to the same principle §17.11 states: a task executor (and, by
extension, its resolver — the restart-time half of the SAME executor's authority over
what it dispatched) never persists or serves an `artifact_path` it did not itself
construct, full stop, regardless of which side of a process boundary — OR a restart —
the untrusted value tried to enter from. `artifacts.resolve()`'s containment check
remains the last line of defence for a genuinely escaped path; it was never meant to be
the ONLY defence against a same-root substitution, which is a different attack shape
entirely.

## Round-1 review fixes summary (issue #345)

- **BLOCKER** — cross-task `artifact_path` substitution via a stored marker: fixed, see
  "Artifact-path construction rule" above.
- **MAJOR** — `in_progress` reconciliation was a one-time-only dead end: fixed via
  `tasks.py`'s new periodic `_reconcile_live_all` pass, see "`external_job_id`
  semantics" above.
- **MINOR (a)** — a timeout used to skip the publish step entirely (the transcript was
  destroyed by the cleanup `finally` before ever being read); `run_harness_job` now
  publishes on EVERY exit path (success, nonzero exit, timeout) from one unified code
  location, before cleanup runs.
- **MINOR (b)** — "record it" was the chosen resolution (not "skip the write"): a
  failed/timed-out job's transcript is still written to
  `.claude/assistant/artifacts/<task_id>.log` on disk for direct inspection, but is
  NOT currently reachable via `/assistant/artifact/<task_id>` — `artifacts.resolve()`
  gates strictly on `state == STATE_COMPLETED` (AST-068's existing, untouched
  contract), so a failed task's file is deliberately an orphan from the HTTP
  endpoint's point of view. Broadening `artifacts.resolve()` to also serve failed-task
  artifacts is out of this task's scope (artifacts.py is AST-068's module boundary).
- **MINOR (c)** — `timeoutSeconds`/`pollIntervalSeconds` are now type/bounds-validated
  (`_validate_number`, bool-before-int-guarded) before anything spawns:
  `1 <= timeoutSeconds <= 1800` (`MIN_HARNESS_TIMEOUT_SECONDS`/
  `MAX_HARNESS_TIMEOUT_SECONDS`), `0.01 <= pollIntervalSeconds <= timeoutSeconds`.
- **MINOR (d)** — `_decode_external_job_id` now validates the decoded task id against
  `_TASK_ID_RE` (`^[A-Za-z0-9_-]+$`) and rejects `pid <= 0`; see "`external_job_id`
  semantics" above.
- **MINOR (e)** — progress events now carry an honest `pct` field, derived from
  `elapsed_seconds / timeoutSeconds` (capped at 99 so it never claims "done" before the
  actual completed/failed transition). This is a PROXY, not a measure of real task
  progress — an agentic run has no native progress signal at all (unlike, say, a file
  upload with a byte count), so elapsed-time-against-budget is the best available
  approximation, and it is documented here as exactly that: a rough "how much of its
  time budget has this job used" indicator, not "how much work is actually done."
