## §13.3 — CHANGED (liveness + honest voice-span statuses, issue #474)

**Section changed**: §13.3 (Voice metrics).

**Before** (SPEC-ASSISTANT.md, current text):

> §13.3 Voice metrics (STT/TTS spans) join the same trace stream.

**After** (final, paste-ready replacement text):

> §13.3 Voice metrics (STT/TTS spans) join the same trace stream. A dead STT engine
> SHALL NOT be indistinguishable from a live one: THE SYSTEM SHALL detect, within a
> bounded window, an STT session that stops producing evidence of life (no result, no
> native error, no native end event) and surface it as an honest terminal `stt-end`
> span with `status: "error"`, never leaving the mic control's visible "listening"
> state outliving a dead engine. An `stt-end` span's `status` SHALL be one of `"ok"`
> (a transcript was produced), `"error"` (the engine failed, including a
> liveness-detected death), `"no-speech"` (the user cancelled before any speech was
> captured), or `"interrupted"` (a still-open turn was closed by something else, e.g.
> a reply's echo-guard interlock pausing an in-progress capture) — never left
> permanently open.

**Why**: Issue #474 (P0, human-reported, live, filed AFTER #464's fix already merged)
reported "talks non-stop, hears nothing at all" — a whole class of failure where the
STT engine silently died while the mic control kept showing "listening" against a
dead recognizer. Investigation of the four hypotheses the issue named:

- **Confirmed root cause** — the browser's own continuous `SpeechRecognition` session
  can end on its own (a documented real-world failure of continuous Web Speech
  sessions, e.g. a service-side idle/network timeout) and nothing in the template
  listened for `onend` at all. `onend` is the ONE event the spec guarantees fires last
  regardless of how recognition stopped, so this alone explains the reported shape:
  the engine died, `onend` fired into the void, and the UI never learned.
- **Confirmed, separate race** — `SpeechRecognition.stop()` is asynchronous; if
  `start()` is called again (a new turn) before the previous native recognizer has
  fully wound down, a stale/leaked instance's late events could reach the CURRENT
  session's shared buffer/state.
- **Confirmed, second mechanism for the same race** (found by reviewer-454's
  retroactive review of the merged #454 batch, folded into this delta) —
  `onSttText(text, turnId)` gated ONLY its terminal span emission on
  `window.__sttSpanId === turnId`; `stopStt()`/`releaseSttCapture()`/
  `queueOrSendChat()` ran unconditionally for an already-superseded turnId.
  Reachable via whisper's async `/transcribe`: start turn A, manually stop it before
  the response arrives, start turn B — A's late response would stop the shared engine
  singleton mid-B, tear down B's live capture state, and forward A's stale text as a
  fresh message. Fixed by gating the WHOLE handler on the same turnId check.
- **Investigated and ruled out** — the silence-timeout endpointing's empty-buffer
  finalize path never stops or clears the engine and never calls `onResult` with
  empty text; it is a harmless no-op, not a cause of the reported symptom.
- **Confirmed, "one honest ending per turn" violated at both stop sites** (review
  round 1, reviewer-454's retroactive review of this branch's own commits) —
  `toggleSttListening`'s manual-stop branch (pre-existing, #454 round 2) and
  `speakReply`'s interrupted-span block (introduced by this branch) both snapshot
  `window.__sttSpanId` BEFORE calling `stopStt()`, then unconditionally emit a
  terminal span off that snapshot. But `stopStt()` → `engine.stop()` → `_finalize()`
  can flush a BUFFERED segment SYNCHRONOUSLY through `onResult` → `onSttText`, which
  already closes the SAME span (`status: "ok"`, text sent) and nulls
  `window.__sttSpanId` before `stopStt()` even returns — producing a double terminal
  span (`["ok","no-speech"]` or `["ok","interrupted"]`) for one turn. Fixed at both
  sites by re-comparing the LIVE `window.__sttSpanId` against the snapshot AFTER
  `stopStt()` returns, only emitting if the span is still open. **Buffer-disposition
  call**: a synchronously-flushed buffer at either site is still SENT (status `"ok"`),
  not discarded — the same "never lose captured speech" precedent #454 already set
  for a manual stop (its own rationale: "flushes whatever's been captured so far
  immediately rather than losing it"). Discarding a real, already-spoken fragment on
  interrupt would reintroduce exactly the failure class #474 exists to fix (silently
  losing what the user said), so the guard alone is the fix — no new "abort/discard"
  engine behavior was added.
- **Liveness backstop, hard requirement regardless of the above** — even if NOTHING
  native ever fires (no `onaudiostart`/`onresult`/`onerror`/`onend`, the truly silent
  case), the engine must not be able to sit "listening" forever. A bounded watchdog is
  the only mechanism that can catch this case, since there is no native event to hook.

This is a spec-level change (not just a bug fix) because it adds a new observable
contract — a bounded liveness guarantee — and a new terminal span status
(`"interrupted"`) that trace consumers (the inspector, `groupTurnsById`) need to know
about, per §13.3's own role as the contract for what a voice span's shape means.

## Implementation notes (this task, #474 — not a further spec amendment)

- `WebSpeechSttEngine` (`plugins/spec-workflow/templates/neural-view.html`) gained:
  - `r.onend`: an unexpected end (no manual `stop()`, no prior `onerror`) reports an
    honest `"web-speech-ended"` error through the SAME `onError` callback `startStt`
    already wires to the standard error-handling path (`releaseSttCapture()`,
    `reportSttFailure()`, an `stt-end` span with `status: "error"`) — no new UI path,
    reuses the existing one.
  - A monotonic session generation (`this._gen`), bumped on every `start()`. Every
    native handler closes over the generation it was created for and no-ops once
    superseded — this is what tells a legitimate late result (same generation, no
    `start()` called since) apart from a truly stale one (generation bumped by a
    subsequent `start()`), rather than blanket-nulling the old recognizer's handlers
    (which would also block the legitimate "one more result for audio already
    captured" behavior `stop()` does not discard).
  - `STT_WEBSPEECH_LIVENESS_MS` (8000ms): a watchdog armed on every `start()`,
    cleared by any native evidence of life (`onaudiostart`, `onresult`, `onerror`,
    `onend`). If nothing clears it in time, the engine is declared dead via the same
    `onError` path, with `this.recog` explicitly torn down (handlers nulled,
    `abort()`/`stop()` called) since a dead engine has no further legitimate results
    pending.
- `WhisperSttEngine` gained the same honesty for its own engine: `MediaRecorder`'s
  `onerror` event (previously unhandled) now reports `"whisper-recorder-error"`
  through `onError` and releases the mic stream, instead of leaving a dead recorder
  behind a "listening" UI.
- `speakReply`'s echo-guard interlock (docs/design/ast-E5.md's "pause recognition
  before a reply speaks") now closes an interrupted turn's OPEN `stt-end` span
  (`status: "interrupted"`) if one exists, snapshotting `window.__sttSpanId` before
  `stopStt()`/`releaseSttCapture()` run — mirroring the pattern
  `toggleSttListening()`'s own manual-stop path already established for the
  no-speech-cancel case. Previously this path left the interrupted turn's span
  permanently open (stopStt() alone emits nothing, per #452), since nothing checked
  for one.
- No engine.py / HTTP changes: the liveness signal is page-local state (per
  docs/design/ast-E5.md — the engine stays text-in/text-out, audio and its lifecycle
  never cross HTTP). `"interrupted"` rides the SAME `POST /assistant/voice-event`
  bridge AST-051 already built; `status` is not enum-validated server-side, so no
  `engine.py` change was needed to accept it.
