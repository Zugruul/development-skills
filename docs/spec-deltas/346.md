## §11.8 — CLARIFIED: capability-gap MECHANICS (AST-071; production wiring deferred to #508)

**Section**: §11.8 (Capabilities/skills & roster).

**Current text** (SPEC-ASSISTANT.md, unchanged — no SHALL wording is being
added, removed, or reworded by this task):

> §11.8 WHEN a request matches no enabled capability THE SYSTEM SHALL say so
> in-persona and MAY offer to acquire the ability by drafting a plan into the
> brain repo (parking lot); installation/enablement SHALL require human
> approval.

§11.8's text is a one-sentence contract; docs/design/ast-E6.md sequence 5
narrows it slightly ("nearest enabled abilities... from the index, not a
fresh LLM guess") but still leaves several mechanics genuinely open. **This
task (AST-071) builds the mechanics only** — gap detection, refusal
rendering, the acquire-offer plan-note draft/mint path, and tracing — as a
complete, directly-callable, fully-tested library + engine method. Wiring
that mechanism into a real, live request path (deciding WHEN a user's
message genuinely warrants the flow) is explicitly **out of scope for #346**
and tracked as its own task, **#508**, per an orchestrator scope decision in
review round 1 (the round-1 reachability finding below is exactly why: no
sound, deterministic trigger exists yet). This delta records every decision
made in building the mechanics so #508 (and any other future consumer) does
not have to re-derive them, or re-discover the round-1 findings the hard way.

### 1. What counts as "no match" (gap detection)

Implemented as `turns.capability_gap_reply(index, user_message, ...)`
(`plugins/spec-workflow/scripts/assistant/turns.py`): it re-runs the SAME
`capability_index.roster_for_turn(index, query, top_n)` evaluation the
turn's own roster injection already performs (Sec11.3, no index recompute,
§17 invariant 7 — never blocks/recomputes) and treats the result as a gap
**only** when that call returns a plain empty list. `roster_for_turn`
already distinguishes three outcomes; only one of them is a gap:

- a real candidate list → not a gap (a usable match exists);
- `AskInsteadOfGuess` (a tie or a low-confidence single winner) → not a gap
  either — Sec11.3's own ambiguity handling is a **different**, already-
  shipped (AST-061) concern: something plausibly matched, it is just
  unclear which; §11.8 is about NOTHING matching at all;
- a plain `[]` → the gap. `capability_index.py`'s own `roster_for_turn`
  docstring already flagged this exact branch as "AST-071's capability-gap
  handling, not this task" before AST-071 existed, and it collapses two
  sub-cases into one: a completely empty index (nothing installed/enabled
  at all) and a nonempty index where nothing had any relevance signal for
  this specific query. Both degrade through the same code path; the
  `text` rendering (below) is what distinguishes them for the reader.

### 2. "Nearest enabled abilities" ranking, and a round-1 reachability finding

`capability_index.nearest_entries(index, query, top_n=DEFAULT_NEAREST_TOP_N)`
is a deliberate SIBLING of `roster_for_turn` — same `_score` function
(embedding cosine when both sides have one, Jaccard keyword-overlap
fallback otherwise), same deterministic `(-score, name)` sort, but with
`roster_for_turn`'s tie/low-confidence GATES removed: naming "the closest
thing I have, though it may not cover this" is more honest, in a refusal,
than naming nothing merely because nothing cleared an invocation-grade
confidence bar (those gates exist to protect INVOCATION, never guess which
capability to actually run — a refusal is not an invocation).

**Round-1 fix (HIGH #1) — zero-score entries are now EXCLUDED.** The
original version had no such filter: it sorted every entry by `(-score,
name)` regardless of score, so an index whose entries ALL scored 0.0
against the query still returned `top_n` of them, in plain alphabetical
order — indistinguishable, to any caller, from a genuine relevance ranking.
`nearest_entries` now returns only entries with `score > 0.0`, and degrades
to `[]` when none qualify (covering both a genuinely empty index and a
nonempty one with zero relevance signal).

**Architectural consequence, proved, not a bug**: `roster_for_turn` returns
`[]` if and only if its max-scoring entry's own score is `<= 0.0` — and
since `_score` never returns a negative number, that condition means EVERY
entry scored EXACTLY 0.0. `capability_gap_reply` calls `nearest_entries`
with the SAME `index`/`query` (hence the SAME `_score` results) immediately
after observing `roster_for_turn(...) == []`. Therefore **`nearest` is
provably always `[]` for every gap `capability_gap_reply` can currently
detect** — the "name specific nearest abilities" refusal shape (shape 3
below) is fully implemented and independently unit-tested
(`section-capability-roster.sh`'s `nearest_entries` cases,
`section-assistant-turns.sh`'s direct `_render_capability_gap_refusal`
call) but is **not reachable through `capability_gap_reply`'s public entry
point today**. Only `total_enabled` (zero vs. nonzero) varies across real
calls. This is documented prominently in both functions' docstrings.
**#508 (or any future task) that wants a refusal to actually name a
specific candidate needs a gap-detection signal weaker than
"`roster_for_turn` returned `[]`"** — e.g. reacting to a LOW-CONFIDENCE
`AskInsteadOfGuess` differently for an explicit invocation attempt vs.
ordinary roster injection, which this task deliberately does not attempt
(see the wiring section below for why).

**Embedding-mode inertness (review round 2, NEW-3 — moved here from a test
comment in `section-assistant-engine.sh`)**: the "EXACTLY 0.0" condition
above is trivial to hit on the deterministic Jaccard keyword-overlap
fallback (two disjoint keyword sets score literally `0/n = 0.0`), but in
production, when a real embeddings capability IS available, `_score` uses
cosine similarity instead — and a real embedding model's cosine similarity
is essentially NEVER exactly `0.0` for two pieces of real text, even when
they are semantically unrelated (small positive or slightly negative
values are the norm; `_score` clamps negatives to `0.0` but a genuine exact
zero from a real model is a coincidence, not a reliable signal). This means
that **in embedding mode, `roster_for_turn() == []` — and therefore this
entire capability-gap flow — may rarely if ever fire in practice.** As
shipped, the flow reliably engages only when the embeddings capability
itself is unavailable or degraded (forcing every `CapabilityIndexEntry.
embedding` to `None`, which drops `_score` to the keyword-overlap
fallback for every comparison). This is a known, accepted limitation, not
fixed by this task — **#508 owns deciding whether/how the gap flow should
also engage in embedding mode** (e.g. an epsilon threshold near zero
instead of a strict `> 0.0`/`<= 0.0` cutoff, or a different detection
signal entirely). `section-assistant-engine.sh`'s integration test for
`_capability_gap_check` explicitly forces the keyword-overlap fallback
(`capability_index._default_embed_fn = lambda texts: None`) for exactly
this reason — without it, the test would be flaky depending on whether the
runtime environment has a working embeddings capability.

### 3. THREE refusal shapes (round-1 addition; round-2 wording fix)

`turns._render_capability_gap_refusal(nearest, total_enabled,
available_count)` — the original two-shape version conflated "nothing
installed" with "something is installed but none of it is relevant", which
reads to a user as the same honest admission when it materially is not (an
operator who installed a capability wants to know their assistant HAS one,
just not a matching one). Now three:

1. `total_enabled == 0` — nothing enabled at all: *"I do not have any
   abilities enabled right now, so I cannot help with that — there is
   nothing installed to try."*
2. `total_enabled > 0`, `nearest` empty — *"I have N abilities enabled (M
   available), but none of them are related to that request."* No names
   listed (there is nothing truthful to name). **Per §2 above, this is the
   ONLY populated-index shape `capability_gap_reply` can currently
   produce.** **Round-2 fix (NEW-5)**: `total_enabled` (`N`) is
   `len(index.entries)`, which — per the "two invisibility tiers" design
   (capability_index.py's own module docstring) — counts every ENABLED
   entry, including enabled-but-UNPROVISIONED ones. Stating only "N
   enabled" without qualification overstated what was actually usable when
   some of those N were unprovisioned; the shape now also states
   `available_count` (`M`, entries with `provisioned_ok`) so an operator
   can tell "enabled" and "actually usable right now" apart.
3. `nearest` non-empty — names each one, ranked, with its `one_liner`.
   **Naming policy for enabled-but-unprovisioned entries (§11.4
   interaction, decided)**: named WITH the `unavailable_reason` (e.g.
   "renderer: renders things (unavailable — binary not on PATH)").
   Silently omitting it would hide that it exists at all; presenting it as
   usable would violate §11.4 ("never present an unavailable ability as
   usable") directly. Not reachable via `capability_gap_reply` today (§2),
   but directly unit-tested so the branch cannot silently regress. This
   shape does not repeat shape 2's N/M summary — per-entry availability is
   already precise here (each unavailable entry states its own reason).

### 4. The MAY-offer plan note — unconditional (round-1 fix reversed by round-2 NEW-2)

**Round 1 (LOW #6)** flagged that the original version always drafted a
plan-note payload whenever a gap was detected — a constant `True` in all
reachable cases, "MAY" implying a decision that never actually varied.
Round 1's fix gated drafting on `total_enabled > 0` (an established
capability posture worth extending). **Round 2 (NEW-2, orchestrator
decision) REVERSED that gate**: the plan note is now drafted
UNCONDITIONALLY on every gap, including a totally bare index
(`total_enabled == 0`). Recorded rationale (on task #508): the bare-
assistant case is exactly the one whose unmet requests are MOST worth
parking — it is the single strongest signal that something should be
acquired, so round 1's gate was suppressing the most useful case rather
than a marginal one. This is now the simplest possible reading of "MAY"
that stays fully deterministic (never a fresh LLM guess about whether to
bother); drafting is cheap and a human still has to approve any real
acquisition out-of-band regardless (Sec11.8), so an always-drafted note is
never itself a commitment. The `plan_note_drafted` trace-event field (round
1's honesty signal for the old, gated version) was **dropped entirely**
(round 2, NEW-2) — with drafting now unconditional, the field would always
read `True` and carry no information.

**Round-2 fix, HIGH NEW-1 — `total_enabled` is now carried in the payload
and is what `mint_gap_note` branches on, not `nearest`.** Review round 2
reproduced a live bug: because `nearest` is provably always `[]` for every
gap `capability_gap_reply` can detect (§2), the PREVIOUS version of
`mint_gap_note` — which branched its note body on whether `nearest` was
non-empty — rendered "No capabilities are currently enabled at all" in
EVERY minted note, even when the SAME gap event's refusal text correctly
said "I have 2 abilities enabled...". A live, self-contradicting note.
`turns._draft_capability_acquire_offer(user_message, nearest,
total_enabled)` now includes `total_enabled` in its payload
(`{"request_excerpt", "nearest": [name, ...], "total_enabled": int}`), and
`distill.mint_gap_note`'s body now branches on THAT field: `total_enabled
== 0` → "No capabilities are currently enabled at all"; `total_enabled > 0`
(with `nearest` empty, the shape it always reaches in practice) → "N
capabilities are currently enabled, but none matched this request."; a
non-empty `nearest` (not reachable via `capability_gap_reply` today, but
still handled for direct callers) still lists the named candidates. The
minted note and its sibling refusal text now always agree.

**Consequence for slugs**: since `nearest` is always `[]` in every
production `mint_gap_note` call, `_gap_note_slug`'s `names_part` always
falls back to the literal `"unspecified"` — **production slugs read
`capability-acquire-plan-unspecified-<hash>` until a future task (§508 or
otherwise) gives `capability_gap_reply` a real per-gap nearest-ability
signal to key off** (see §2's architectural finding for why `nearest` is
empty in the first place). This is expected, not a bug in the slug scheme
itself — dedup still works correctly (identical normalized excerpts still
collapse to the same `unspecified-<hash>` slug; different ones still get
distinct hashes).

`turns.py` never mints anything and never touches a queue itself
(Sec9.5/§17 invariant 7; enforced by the existing `NO_QUEUE_TOUCH`/
`NO_ENGINE_IMPORT` invariant tests in `section-assistant-turns.sh`, which
re-scan the whole module's source and therefore also cover all of this
task's code). The payload is handed to `distill.mint_gap_note` via
`engine._enqueue_gap_note` (mirrors `_enqueue_artifact_note`'s non-
blocking, drop-oldest-on-overflow posture onto the SAME `distiller` queue
— the engine's one sanctioned brain-write thread). The minted note is
tagged `capability-acquisition-plan,parking-lot`, titled as a plan (not a
capability), and its body states in plain text that nothing was installed
and a human must approve any acquisition — `mint_gap_note` contains no
installation logic whatsoever and never touches `assistant.capabilities.*`
or project.yaml (verified by a byte-identical project.yaml assertion in
both `section-assistant-distill.sh` and `section-assistant-engine.sh`).

### 5. Slug dedupe — re-keyed (round-1 fix, MEDIUM #2)

The original slug was a 40-char prefix of the slugified excerpt
(`capability-acquire-plan-<prefix>`). Two independent bugs, both
demonstrated with regression tests before the fix
(`section-assistant-distill.sh`):

- **Flooding**: near-identical requests that diverged in their first 40
  characters got DISTINCT slugs, minting a fresh note per near-duplicate
  turn.
- **Silent data loss**: two DIFFERENT requests sharing a 40-character
  prefix collapsed onto ONE slug — the second mint's `brain.mint()` bump
  silently overwrote the first request's note content instead of creating
  its own.

`distill._gap_note_slug(nearest, excerpt)` re-keys on the SORTED
nearest-capability names plus a short hash (`sha256[:10]`) of the
`_normalize_gap_excerpt`-normalized (lowercased, whitespace-collapsed) FULL
excerpt — not just its first 40 characters. **Collision semantics
(documented, not a bug)**: two requests naming the same nearest-capability
set whose excerpts normalize identically dedupe into one note by design
(that IS "the same request", modulo case/whitespace); anything else,
including a difference past the old scheme's 40-char cutoff, now hashes
differently and gets its own note. A 10-hex-char (40-bit) hash has a real
but astronomically small collision probability for this note volume — an
accepted trade-off, not fixed further. **Non-ASCII limitation (documented,
left as-is per round-1 guidance)**: Python's locale-naive `str.lower()`
does not round-trip cleanly for every script, so two visually-identical
non-ASCII excerpts can rarely normalize to different strings and mint
separate notes instead of deduping — a minor over-minting edge case, never
a data-loss one.

**Round-2 note (NEW-4)**: `_gap_note_slug`'s docstring originally described
the two bugs above as a single garbled run-on sentence that did not parse
cleanly (conflating the flooding and silent-data-loss cases). Repaired to
state each bug as its own clear point, matching the wording above.
**Round-2 note (see §4)**: because `nearest` is always `[]` in every
production call (§2's architectural finding), `names_part` always falls
back to `"unspecified"` today — production slugs read
`capability-acquire-plan-unspecified-<hash>` until a future task gives
`capability_gap_reply` a real per-gap nearest-ability signal.

### 6. Trace event kind — `skill.gap`, not `capability.gap` (round-1 fix, LOW #4)

§10.1 enumerates first-class event-kind namespaces: `turn.*, recall.*,
prompt.*, provider.*, skill.*, distill.*, task.*, tts.*, stt.*`.
`capability.gap` (the original choice) was outside all of them. Renamed to
`skill.gap` (success/detection path) and `skill.gap.error` (failure path,
see below) — both inside the enumerated `skill.*` namespace.

### 7. Errors are first-class events too (round-1 fix, LOW #5, §10.6)

`engine._capability_gap_check`'s original `except Exception: return` never
raised into the caller (correct, Sec17) but silently swallowed the
failure — violating §10.6 ("every error... SHALL be a first-class event
linked from its turn"). It now emits a `skill.gap.error` trace event
(`status: "error"`, `turn_id` set, `payload: {error, error_type}`) before
returning, still never raising.

### 8. Wiring — NOT auto-invoked from any real request path (#508's scope, not #346's)

`engine._capability_gap_check(root, turn_id, message)` is a complete,
directly-callable method: on a gap it emits the `skill.gap` trace event
(turn-linked, §10.1) and enqueues the plan-note draft, never touching a
reply, never raising into the caller (errors become `skill.gap.error`
events per §7 above).

It is **deliberately not called from `_chat`, nor from any other live
request path**. This was tried first (auto-invoking from `_chat` on every
turn) and reverted after a concrete, reproduced regression: calling it
unconditionally on every turn made an 8-turn conversation against a
skill-less assistant fixture (the ordinary v1 state for an assistant with
no `.claude/skills/*` installed yet) mint 8 near-duplicate acquire-offer
plan notes — one per turn — instead of the single real distilled-batch note
that conversation should produce. This broke
`section-assistant-distill.sh`'s pre-existing "N turns through the real
engine trigger a real distilled mint" integration test outright, and is
exactly the flooding failure mode a careful reading of Sec11.3 already
warns about for roster injection: `_roster_provider_for`'s own docstring
establishes that "ordinary chat turns with no relevant capability at all...
are completely unaffected." `roster_for_turn` returning `[]` cannot, by
itself, distinguish "this message is an action request my assistant cannot
fulfill" from "this message is ordinary conversation that happens not to
mention any installed capability" — and §11.8 itself rules out the one tool
that could make that distinction ("not a fresh LLM guess"). No
deterministic, stdlib-only substitute reliably tells the two apart without
either missing real gaps or flooding the brain on ordinary/off-topic turns.

Review round 1 confirmed this finding was correct and formally re-scoped
production wiring as **task #508**: whoever builds #508 needs a REAL
trigger — e.g. a genuine capability-invocation-attempt path (docs/design/
ast-E6.md sequence 2, "turns.py's pipeline resolves a capability from the
turn's roster" — not yet built as of this task) whose own resolution comes
up empty — and per §2 above, may also need to loosen the gap-detection
signal itself if named-ability refusals (shape 3) are meant to actually
fire in practice. `_capability_gap_check` is shipped ready for that: the
same call shape `section-assistant-engine.sh`'s integration tests already
exercise directly.

A regression guard (`section-assistant-engine.sh`, "ordinary chat mints
exactly one note... never a flood") pins the current (unwired) state so a
future change that re-introduces the flooding behavior fails loudly.

## §17 invariants — unaffected, verified

None of the ten invariants in §17 change. This task's tests specifically
verify it does not weaken any of them:
- Invariant 5 (atomic + serialized brain writes): `mint_gap_note` writes
  through `brain.mint()`'s identities-wide flock exactly like every other
  minter in this codebase — no new write path.
- Invariant 7 (turns never block): `turns.py` stays queue-free (existing
  invariant tests re-verified against the new code); `_enqueue_gap_note`
  is `put_nowait`-only, drop-oldest on overflow, same as every other
  enqueue helper in `engine.py`.
- Invariant 4/§11.8 itself (no installation without human approval):
  `mint_gap_note` and `_draft_capability_acquire_offer` never read or
  write `assistant.capabilities.*` or project.yaml — asserted directly
  (byte-identical project.yaml before/after) in both
  `section-assistant-distill.sh` and `section-assistant-engine.sh`.
- §10.1/§10.6 (event namespace + first-class errors): `skill.gap`/
  `skill.gap.error` are inside the enumerated `skill.*` namespace, and
  every internal failure of `_capability_gap_check` is now a linked,
  turn_id-carrying trace event rather than a silent swallow.
