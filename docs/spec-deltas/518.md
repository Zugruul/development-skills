## §8.4 — CHANGED (codex turn sandbox mode: conditional read-only → workspace-write, issue #518)

**Section changed**: §8.4 ("Turns SHALL run answer-only: adapters SHALL pin isolation
flags (no user-global instruction ingestion; no plugin/skill surface from the dev
workflow; harness tool use disabled)."), as implemented by `codex.py`'s
`_PINNED_FLAGS`/`_WRITE_FLAGS`.

**What changed**: a codex-backed turn whose context carries a `fileOutputDir` (the
engine resolved a sanctioned per-assistant output directory for this turn, per
`engine.py`) now runs with `-s / --sandbox workspace-write` instead of `-s read-only`,
still paired with `-C <isolated per-turn workdir>`. A turn with no `fileOutputDir`
keeps `-s read-only` exactly as before this task — this is a two-flag-set design,
gated on the same key claude.py's own `_PINNED_FLAGS`/`_WRITE_FLAGS` split already
gates on, not an unconditional widening of every codex turn's sandbox.

**Why**: fee53259 built a workdir-publish relay — the persona output contract
(`setup.py`'s OUT block; `turns.py`'s `fileOutput` system-prompt text) tells every
assistant its turn workdir is writable and that files it writes there get published
into the brain's media library after the reply. fee53259 wired this correctly for the
claude adapter (`claude.py`: `--tools Write --allowedTools Write --permission-mode
acceptEdits` scoped to an isolated cwd, `complete()` moves files out of it into
`fileOutputDir` in its `finally` block — empirically validated live against the real
claude CLI per that commit's message) but never wired the codex half: `codex.py` kept
`-s read-only` unconditionally and never read `context["fileOutputDir"]` at all. Every
codex-backed persona's turn workdir was therefore never actually writable, and no
publish step existed even if it had been — a real gpt-5.6-sol turn asked for a 3D model
and replied "I can generate the model, but file creation is blocked by the current
read-only sandbox, so I couldn't save the .obj and .mtl files." The two output
contracts (promise vs. actual sandbox) were flatly contradictory for the codex path.

**Contract now**:
- `codex.py`'s `_build_argv` picks `_WRITE_FLAGS` (`-s workspace-write`) when
  `context.get("fileOutputDir")` is truthy, `_PINNED_FLAGS` (`-s read-only`)
  otherwise — the same shape as claude.py's pre-existing `_PINNED_FLAGS`/
  `_WRITE_FLAGS` split (fee53259), applied to codex for the first time here.
- `codex.py`'s `complete()` gained the SAME workdir-publish step `claude.py` already
  had, now factored into one shared, hardened `adapters.publish_workdir_files`
  (round-1 review, see below): when `fileOutputDir` is present, every eligible file
  sitting in the `-C` workdir is moved into that directory before the workdir is torn
  down.
- `codex.py`'s `complete()` also now pins `cwd=workdir` on the `invoke_cli` call
  (round-1 review) as belt-and-suspenders alongside `-C` — matching harness.py's own
  codex-path precedent (`subprocess.Popen(argv, cwd=workdir, ...)`) and claude.py's
  `cwd=` (its only mechanism, having no `-C` equivalent at all).
- Every other pinned isolation flag is unchanged: `--skip-git-repo-check`,
  `--ignore-user-config`, `--ignore-rules`, `--ephemeral`, the isolated per-turn
  `CODEX_HOME` (auth.json copy only, no AGENTS.md), and the mandatory timeout.

**Round-1 review hardening (both adapters, shared code)**: the publish loop itself
(originally duplicated inline in claude.py and, for this task, codex.py) moved into
one shared `adapters.publish_workdir_files(workdir, publish_dir)` that both adapters
call, fixing two real vulnerabilities a reviewer reproduced live:
1. **Cross-filesystem silent loss**: the original loop used a bare `os.replace`
   wrapped in `except OSError: pass`. `os.replace` cannot cross filesystem
   boundaries (EXDEV) — a RAM-disk temp root reproduced total silent loss of the
   published file. The shared helper now falls back to `shutil.copy2` + `os.remove`
   when `os.replace` raises, so the file lands either way; same-filesystem moves stay
   the original atomic `os.replace`.
2. **Symlink/hardlink publish channel**: a model-written SYMLINK or a file with
   `st_nlink > 1` (a HARDLINK) in the workdir would previously be moved/copied like
   any other file — since neither operation follows/dereferences safely in a way that
   prevents it, this let a hostile turn "publish" a link to (or another name for) an
   arbitrary file this process can already read, serving its real content through the
   chat media library / `/file` route as if the model had produced it. The shared
   helper now skips any `os.path.islink` entry and any regular file whose `st_nlink >
   1`, for both adapters.

**Known edge, documented not silent**: a persona configured with `fileOutput: false`
never gets a `fileOutputDir` injected (`engine.py`), so its codex turns keep the OLD
unconditional `read-only` sandbox and behavior — but `setup.py`'s OUT block and
`turns.py`'s file-output prompt text are not conditioned on that same flag, so such a
persona's system prompt can still claim file output is possible while its actual
sandbox refuses it. Narrowing that prompt text to the per-persona `fileOutput` flag is
out of this task's scope; flagged here rather than left to be rediscovered as a
"new" live refusal.

**Why this still satisfies §17.2** ("harness subprocesses always run with pinned
isolation and sandbox flags — the pair constitutes the boundary"): the pair itself
(sandbox mode + `-C` isolated directory) is still pinned in BOTH branches — only the
pair's *values* differ by branch, from `(read-only, isolated dir)` for a
no-file-output turn to `(workspace-write, isolated dir)` for a file-output turn. The
workspace-write branch reuses the exact same confinement shape `harness.py` already
established for harness jobs (§9.4: codex harness jobs always run `-s workspace-write`
+ `-C <isolated dir>`) — this fix reuses that already-reviewed and already-accepted
boundary argument for turns' file-output case rather than inventing a new one. The
write surface is exactly the isolated `-C` workdir; the workdir-publish relay
(hardened per above) is the sole consumer of anything written there. This is a
confinement claim, not an absolute-isolation one: harness.py's own module docstring
accepts that a shell tool codex spawns could in principle write somewhere else inside
the shared OS temp root but outside `-C` ("TMPDIR leakage") — this fix accepts that
exact same, already-reviewed residual risk for the workspace-write branch (moot for
the read-only branch, where no write is possible at all), rather than claiming
`-C` makes writes provably impossible anywhere outside it.

**GAP, unchanged from before this fix** (documented in `codex.py`'s own module
docstring, originally flagged under AST-011): codex-cli 0.144.4 has no discovered flag
that fully disables the model's ability to *request* a tool/shell call mid-turn — `-s`
only bounds what such a call may *do*, in whichever branch is active for this turn.
§8.4's "harness tool use disabled" clause was already an approximation for codex turns
(never a hard guarantee the way `claude.py`'s `--tools ""` is for its non-file-output
path) — this fix does not weaken that approximation beyond what claude.py's own
already-accepted `fileOutputDir`-present exception (`--tools Write`, scoped) already
established for the claude path. Bringing codex to parity, not introducing a new
class of exception.

**Investigation note (claude-path status, verified not guessed)**: fee53259's own
commit message states the claude-path write ("--allowedTools Write + acceptEdits")
was "validated live" against the real claude CLI — the claude adapter's file-write and
publish relay were already working correctly before this task; the bug was scoped
entirely to the codex adapter never having received the equivalent argv/publish
changes fee53259 made for claude. fee53259 itself shipped with zero tests covering
either adapter's relay; round-1 review of this task added the missing claude-side
happy-path relay test alongside the new codex-side coverage.
