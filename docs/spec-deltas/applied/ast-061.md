## §11.3 — CLARIFIED (the precise tie/low-confidence -> ask rule)

§11.3 reads: "...the per-turn roster SHALL be relevance-filtered top-N with a hard cap;
ties/low confidence → the assistant asks instead of guessing." Read literally this could
mean EITHER "a top candidate that is merely weak" OR "a query that matches NOTHING at
all" both count as "low confidence" and both should trigger an ask. AST-061 needed one
precise, deterministic rule to implement and test against, so this delta makes the
distinction explicit:

- **Zero relevance is not "low confidence" — it is "no candidate".** When the
  BEST-scoring entry's normalized relevance score is exactly `0.0` (no capability shares
  any signal with the turn's query at all), `capability_index.roster_for_turn` returns an
  EMPTY roster, not the ask sentinel. Treating every ordinary, capability-unrelated chat
  turn as "low confidence, please ask" would make the assistant interrupt normal
  conversation constantly (an assistant with any capabilities installed at all would ask
  a clarifying question on nearly every turn that isn't explicitly about one of them).
  That failure mode — no plausible match at all — is §11.8's "request matches no enabled
  capability" case (AST-071, out of this task's scope), not §11.3's ask-instead-of-guess.
- **"Ask instead of guess" fires only when there WAS a plausible signal.** Two shapes,
  both deterministic and both requiring at least one entry with a NONZERO score:
  - **Tie**: two or more entries share the single best (nonzero) score.
  - **Low confidence**: the single best (nonzero) score is below a documented threshold
    (`capability_index.LOW_CONFIDENCE_THRESHOLD = 0.34`) with no tie at that top score.

Both the embedding-cosine path and the keyword-Jaccard fallback are normalized to
`[0.0, 1.0]` (§11.3 does not specify a scoring method, only that ties/low confidence
route to asking) so one threshold constant applies uniformly regardless of which path
scored a given turn — see `capability_index.py`'s module docstring and `_score`'s own
docstring for the exact normalization.

Proposed EARS text, paste-ready for §11.3 (appending the clarifying sentence, the rest
unchanged):

> §11.3 The engine SHALL compile a capability index {name, one-liner, keywords,
> embedding, enabled, provisioned-ok} on start and on change; the per-turn roster SHALL
> be relevance-filtered top-N with a hard cap; ties/low confidence → the assistant asks
> instead of guessing. A turn whose best-scoring capability has NO relevance signal at
> all (a query unrelated to every installed capability) SHALL yield an empty roster, not
> an ask — the ask-instead-of-guess behavior applies only when at least one capability
> plausibly matched but the choice among matches was ambiguous or too weak to trust.

## Bookkeeping this task adds (not a spec amendment, an implementation note)

`§11.1`'s "SKILL.md and optional capability.yaml" already establishes that not every
skill carries a capability.yaml. AST-061's capability index only ever produces an entry
for skills that DO carry one (`capability_index.load_capability`'s `Capability`/
`CapabilityError` values are what an entry is built from) — a skill without a
capability.yaml is a passive, instruction-only skill outside this subsystem entirely,
never a compile failure and never silently indexed with a fabricated invoke/provisioning
shape it never declared. This is a scope reading, not a contradiction of §11.1 (which
never claims every skill becomes an indexed capability), so it is recorded here for
visibility rather than as its own delta section.
