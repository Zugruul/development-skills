## §9.2 Host-neutral checkpoint admission — ADDED

WHEN bundled task selection or a normalized transition to the active board's configured work status is requested, THE SYSTEM SHALL use a shared read-only checkpoint check with the effective configuration, default `.claude/CHECKPOINT`, primary-checkout-relative paths, absolute configured paths and explicit root overrides, independently of host hooks.

WHEN the checkpoint path is present (including an empty flag), or relevant configuration/state cannot be safely inspected, THE SYSTEM SHALL refuse admission with an actionable diagnostic; invalid configured paths SHALL NOT silently fall back to the default.

WHEN `board.sh next` runs while paused, THE SYSTEM SHALL refuse before board network reads or queued replay and emit neither PICK nor RESUME; direct `next.py` SHALL apply the same check using its configured repository's primary state even when invoked outside that repository or from a linked worktree.

WHEN a direct or deferred work-status mutation is requested while paused, THE SYSTEM SHALL refuse before comments-marker lookup, API mutation, new queue append or transition telemetry, including repeated requests, and SHALL retain deferred operations for retry after flag removal.

WHEN already-running work needs to reach a stable boundary, THE SYSTEM SHALL allow other transitions subject to their existing guards and keep gate execution available; general preflight and session-start SHALL report the same configured checkpoint state while preserving advisory/bootstrap contracts.

WHEN pausing or resuming, THE SYSTEM SHALL preserve truthful board state, finish existing work to a safe boundary where possible, write a handoff before stopping, and resume admission only after the flag is removed or invalid state is repaired. Documentation SHALL state that these bundled admission checks do not prevent arbitrary edits, raw git/gh commands, or a flag appearing after a check without an atomic admission lock.

WHEN classifying a work-status transition, THE SYSTEM SHALL honor the active BOARD selection and use `statusFlow[1]` (or `statusFlow[0]` for a single-status flow), matching the picker and preserving its first-board fallback for unknown board ids. Structurally unusable board selection or status-flow configuration SHALL fail closed; unrelated comment, review and closure guard semantics SHALL remain unchanged.
