## §9.4/§11.5/§11.8 — EXTENDED: request -> resolve -> invoke -> (gap), wired into the live turn

**Sections changed**: §9.4 (harness jobs -- the longRunning marker sits
alongside it as a second, lighter-weight async mechanism), §11.5 (`invoke.exec`
-- now actually reachable from a real request), §11.8 (capability gap --
docs/spec-deltas/applied/346.md built the mechanics and explicitly deferred
production wiring to this task; this delta closes that deferral).

**Context**: docs/design/ast-E6.md sequence 2 ("`turns.py`'s pipeline resolves
a capability from the turn's roster") and sequence 5 ("capability gap") were
both designed but never wired into a live request path. AST-061/E6 already
compiles a per-turn roster and injects it into the persona prompt (§11.3), and
AST-063/064 already built the schema-validated argv/MCP invoke primitives
(§11.5/§11.7) -- but nothing in the turn pipeline ever PARSED an intent to use
one of them, called `invoke_capability`, or fed a result back to the model.
Issue #346's capability-gap mechanics were shipped fully tested but explicitly
"not auto-invoked from any real request path", with a documented reachability
finding: the only signal available (`roster_for_turn() == []`) is inert in
production embedding mode (real cosine similarity is essentially never exactly
`0.0`), so the gap flow needed a different, EXPLICIT trigger this task builds.

### 1. The directive: a single, greppable, model-taught syntax

A turn's reply signals a capability request with exactly one fenced code
block, language-tagged `capability`, containing one JSON object:

```
​```capability
{"name": "<capability-name>", "params": {...}}
​```
```

- **One per turn, v1 (hard rule).** Only the FIRST fenced `capability` block
  in a turn's FIRST completion is ever acted on. Any additional block --
  whether a second one in the same completion, or one appearing in the
  same-turn follow-up completion after an invocation -- is parsed (so it can
  be traced), stripped from the visible reply (never leaked as raw JSON
  either way), and IGNORED: a `skill.request` trace event records it with
  `status: "ignored"`. No chaining, no queued sequence of invocations, in v1.
- **`params` is optional**, defaulting to `{}`; if present it must itself be a
  JSON object. `name` is required and must be a non-empty string.
- **Never shown to the user.** The fenced block is removed from the reply
  text before it reaches the user, whether the directive parsed validly or
  not (a malformed directive still never leaks raw JSON). This promise is
  scoped to the EXACT ` ```capability ` triple-backtick fence syntax
  (round-2 review, optional nit): an indented (4-space) code block, or one
  using 4+ backticks instead of exactly 3, is not recognized as a directive
  at all and renders verbatim if a model ever produces one.
- **This IS the signal, not a similarity score.** The roster prompt text
  (`turns._render_roster_entries`, appended whenever the compiled roster has
  at least one real, named entry -- never for an empty roster or the
  `AskInsteadOfGuess` sentinel alone) teaches the model this exact syntax.
  This is what makes the mechanism reachable in embedding mode: the model is
  told the shape and asked to use it explicitly, so detecting a request no
  longer depends on `roster_for_turn`'s relevance-scoring gates at all.
- **Parser**: `turns.parse_capability_directives(reply_text) ->
  (visible_text, directives, actionable)` -- pure, no I/O, returns EVERY
  fenced block found (in order) as a `CapabilityDirective(name, params)` or
  a `CapabilityDirectiveError(raw, reason)` for anything that failed to
  parse as the shape above (round-1 review, finding 2: this INCLUDES an
  unterminated/dangling fence with no closing marker at all -- e.g. a reply
  truncated mid-JSON by a token limit -- which is stripped and reported as
  an error rather than left leaking raw text). The opening fence is
  anchored to the START OF A LINE (`re.MULTILINE`, round-1 review finding
  3) and case-insensitive (a mixed- or upper-case language tag still
  matches). `actionable` is the ONE `CapabilityDirective` this reply's own
  shape actually requests right now, or `None` -- see "the trailing-element
  policy" below. This function still makes no decision beyond `actionable`
  about which directive a caller acts on; the "act on the first actionable
  one, trace-and-ignore the rest" policy itself lives in engine.py.
- **The trailing-element policy (round-1 review, finding 3 -- "teach-then-
  quote").** Review reproduced, live, a model DEMONSTRATING the directive
  syntax mid-explanation ("Here's how you'd ask for it: `​```capability
  ...`​``. But I can't actually run this.") being treated as a real
  invocation. `directives[0]` only becomes `actionable` when it ALSO is the
  reply's TRAILING element: nothing but whitespace (and/or later fenced
  blocks, always ignored anyway under the one-per-turn rule) follows its
  closing fence. A directive followed by more real prose is presumed to be
  an example, not a request -- still stripped from the visible reply
  either way, just never invoked. Combined with the line-start anchor,
  this also means a fence mentioned mid-sentence is never recognized as a
  directive at all (not even as a non-actionable one). **KNOWN v1
  LIMITATION**: in-band signalling inside the model's own free-text output
  is inherently ambiguous; this trailing-position heuristic is a cheap,
  mechanical, mostly-effective mitigation, not a proof of intent. A
  genuine request immediately followed by an unrelated trailing remark is
  currently never actionable, and a sufficiently unusual reply shape can
  still misfire in either direction. This is accepted, not hidden --
  fixing it properly would require actual model-side cooperation (e.g. a
  dedicated tool-call channel outside the free-text reply), which is out
  of scope for v1's in-band mechanism.

### 2. Resolution: by name, never by score

An explicit directive is resolved against the already-compiled
`CapabilityIndex` (§11.3, no recompute in the request path) by EXACT,
case-insensitive NAME match: `capability_index.resolve_by_name(index, name)`.
This is a deliberately different operation from `roster_for_turn`/
`nearest_entries`, which answer "what's plausibly relevant to this free-text
query" -- resolution answers a different question the model already decided
for us: "does the capability I was explicitly told to invoke exist and is it
usable." Per §11.2's two-invisibility-tiers design, a disabled (or
version-incompatible) capability's name never enters `index.entries` at all,
so a directive naming one is indistinguishable at this layer from a directive
naming something that was never installed -- both correctly fail to resolve,
and §17.2 ("a disabled capability is never invoked") holds without this
function needing its own enablement check.

Three outcomes fan out from here:

1. **No match** -> the capability-gap flow (§4 below).
2. **Match, but `provisioned_ok` is false** -> a refusal naming the
   capability and its `unavailable_reason` verbatim (§11.4: "never present an
   unavailable ability as usable"). Traced as `skill.error`
   (`reason: "unprovisioned"`). NOT a gap -- something concrete WAS found,
   it just is not usable right now; conflating this with §11.8's "nothing
   matches at all" would be dishonest in the other direction.
3. **Match, provisioned** -> params are validated (see §3) and the
   capability is invoked (see §5), or -- if it declares itself long-running
   -- queued (see §6).

### 3. Parameter validation: reused, never duplicated

`adapters.invoke_argv`/`invoke_mcp` already validate `params` against the
capability's declared schema (`invoke.params`/`invoke.mcp.params`) BEFORE any
substitution or subprocess spawn, raising `ParamValidationError` on any
violation (missing/type/pattern/allowlist/undeclared). The turn pipeline does
not re-implement or duplicate this check -- it calls
`capability_index.invoke_capability` directly and catches
`adapters.ParamValidationError`, turning it into a refusal (`skill.error`,
`reason: "invalid_params"`) that names what was wrong. "Reject before spawn"
is satisfied by construction (the existing validate-then-substitute-then-spawn
ordering inside `invoke_argv`/`invoke_mcp`), not by a second, possibly-drifting
validation call site in engine.py.

### 4. The gap trigger: explicit, not score-based (closes #346's deferral)

`turns.capability_gap_reply` gains an optional `requested_name` parameter.
When a caller supplies it, the function's ENTIRE gap-detection rule switches:
instead of re-running `roster_for_turn` and checking for an empty list (the
pre-#508 trigger, still used when `requested_name` is omitted, and still
subject to #346's documented embedding-mode-inertness finding), it resolves
`requested_name` by name (§2). A resolving name is never a gap. An unresolved
name IS a gap -- deterministically, regardless of what the raw conversational
message would have scored on its own, and regardless of whether a real
embeddings capability is active. This is the exact "signal that fires in
embedding mode... gap when the model EXPLICITLY requested an action AND
resolution fails, not just score==0" the #346 owner comment asked for.

`nearest` (the "closest enabled abilities" a refusal names, §11.8/#346's
shape 3) is scored on this path from a query built off `requested_name`
itself -- a sharper, more specific signal than the ambient free-text message.
This is why `nearest` is NO LONGER provably always `[]` the way #346's
architectural note proved it was for the pre-#508 trigger: a directive naming
`weather-report` against an index that has `weather` installed now correctly
surfaces `weather` as the nearest candidate, with its own one_liner, in the
refusal. Consequently the minted plan note's slug
(`distill._gap_note_slug`, keyed on sorted nearest names + an excerpt hash)
is no longer permanently pinned to the `unspecified` fallback for THIS call
shape -- it degrades to `unspecified` only when the requested name genuinely
shares no keyword/embedding signal with anything installed, which is now an
honest "nothing close" result rather than an architectural inevitability.

`engine._capability_gap_check` threads `requested_name` straight through to
`turns.capability_gap_reply` and now RETURNS the `CapabilityGap` namedtuple
(previously always implicitly `None`) so its caller can use `gap.text` as the
turn's actual reply -- every pre-#508 caller that ignored the return value is
unaffected. The `skill.gap` trace event's payload also carries
`requested_name` now, alongside `nearest`.

**The flooding guard from #346 is preserved, not loosened.** This gap trigger
only ever fires from inside the directive-driven hook, and ONLY when a
directive was actually parsed with a name that failed to resolve. A plain
chat message with no fenced `capability` block never reaches
`capability_index`, `adapters`, the tasks queue, or ANY `skill.*`/`turn.gap`
trace machinery at all -- `turns.parse_capability_directives` returning an
empty list is checked first and short-circuits everything else. An 8-turn
skill-less conversation still mints exactly the one real distilled-batch
note, never eight near-duplicate gap notes (regression-guarded in
`section-assistant-engine.sh`, extended from #346's own guard).

### 5. Inline invocation: bounded, traced, one same-turn follow-up

A resolved, provisioned, param-valid directive is invoked via the existing
`capability_index.invoke_capability` choke point (argv or MCP, auto-detected,
§11.5/§11.7/§17.2/§17.3 unchanged) under a MANDATORY, bounded timeout:
`engine.CAPABILITY_INVOKE_TIMEOUT_SECONDS` (30s default; a module-level
constant, not per-call config -- deliberately distinct from
`adapters.DEFAULT_TIMEOUT_SECONDS` (60s), which bounds a provider-CLI
completion, a different kind of call). This runs SYNCHRONOUSLY on the HTTP
request thread that is already handling the turn (never a worker thread) --
§9.5's "turns never block on the distiller/index/task queue" is unaffected,
since this is not background work being waited on, it is the turn's own,
explicitly-requested, bounded-time action.

Every invocation attempt is bracketed by `skill.invoke` trace events sharing
one `span_id` (`status: "start"` then `status: "ok"`), `parent_span_id` set
to the turn's own `turn_id` (turn-linked, §10.1). A timeout raises
`adapters.Timeout`, caught and turned into a graceful reply plus a
`skill.error` event (`status: "timeout"`) -- never an unhandled exception,
never an indefinite hang.

On success, the result is rendered to text
(`turns.render_capability_result_text`) and hard-capped at
`turns.CAPABILITY_RESULT_CHAR_CAP` (4000 chars) with an explicit,
human-readable `"... [truncated N chars]"` marker counted WITHIN the cap --
never a silent drop, and never unbounded input into the follow-up completion.
That text drives exactly ONE same-turn, same-session-context follow-up
completion (`turns.render_capability_result_followup` reuses the turn's
ALREADY-composed system prompt verbatim -- persona, roster, recalled notes,
and rolling summary are never recomposed or re-recalled a second time for one
user message, per §9.1/§17.7). The follow-up's reply becomes the turn's final,
user-visible text; every directive found in it (regardless of its own
trailing-position status) is traced `"ignored"` per the one-per-turn rule
(§1) -- NOTHING from a follow-up is ever honored, full stop.

**The follow-up call is itself failure-hardened (round-1 review, finding
4).** By the time the follow-up runs, the capability has ALREADY executed --
a side effect (if any) already happened. Letting the follow-up `complete_fn`
call's `adapters.AdapterError` propagate up to `_chat`'s outer handler would
502 the whole turn with NO exchange ever appended, discarding the executed
outcome entirely and inviting a client retry that would run the SAME
capability again. Instead, the follow-up call is wrapped in its own
`AdapterError` handler: a failure degrades to
`turns.render_capability_completed_fallback(name, result_text)` -- a plain,
result-bearing template reply -- traced as `skill.error`
(`reason: "followup_failed"`), and the turn completes normally (200,
exchange appended). The SAME fallback covers finding 5: a follow-up reply
that strips down to nothing (e.g. the model's follow-up was itself just
another never-honored directive block, with no surrounding prose) falls
back to the identical template rather than returning an empty 200.

**The whole hook runs under one outer exception guard (round-1 review,
finding 8).** Every branch above already degrades a KNOWN failure mode to a
traced error + graceful reply; this closes the gap for an UNKNOWN one -- any
other unexpected exception anywhere in the hook (a mutation-class bug, a
future edit that breaks an invariant the hook relies on) is caught by one
broad `try/except Exception` wrapping the hook body, emits `skill.error`
(`reason: "internal_exception"`), and returns a plain apology reply -- the
SAME "never raise into the caller" discipline `_capability_gap_check`
already established for its own internals, extended to the whole loop. This
guarantees `turn.end` always fires, never a dropped connection with no
terminal trace event.

### 6. Long-running capabilities: the `longRunning` marker

`capability.yaml` gains one additive, optional top-level key:
`longRunning: <bool>` (default `false` when absent -- every capability.yaml
written before this task is unaffected). A capability that declares
`longRunning: true` is never invoked inline; instead its invocation is
enqueued as a `capability-invoke` task (`capability_index.KIND`) via
`tasks.enqueue` under `engine.CAPABILITY_TASK_TIMEOUT_SECONDS` (300s
default), and the turn replies immediately that the work has been queued --
"watch the artifact panel for the result" (round-1 review, one-liner finding
9: the earlier wording, "I will let you know when it is done", promised a
proactive follow-up message this mechanism does not actually send; the
reworded reply matches what §12.5's existing queue-indicator/artifact-panel
path actually does). No inline spawn, chat/voice stay fully usable
throughout (§12.5). **The task timeout is a SEPARATE constant from the
inline path's, not a reuse (round-1 review, HIGH finding 1).** The FIRST
version of this task wired the queued path through
`engine.CAPABILITY_INVOKE_TIMEOUT_SECONDS` (the 30s INLINE bound) by
mistake -- reviewer reproduced a queued capability silently killed at 30s
even though the user had already been told it was safely backgrounded, with
the failure never reaching the conversation at all (directly contradicting
this very section's own text). `CAPABILITY_TASK_TIMEOUT_SECONDS` (300s)
matches `harness.DEFAULT_HARNESS_TIMEOUT_SECONDS` -- the SAME default this
codebase already uses for its OTHER async-task mechanism, for the same
underlying reason: background work has no HTTP request thread to protect,
but `tasks.py`'s worker is a SINGLE SERIAL thread (its own documented
execution model), so an unbounded queued capability would still block every
OTHER queued task (harness jobs included) behind it forever -- a bound
still exists, just a much more generous one than the inline path's. The
queued task's executor
(`capability_index.run_capability_invoke_task`, registered into engine.py's
existing `"tasks"` worker slot alongside `harness.run_harness_job`) runs on
the tasks WORKER thread and dispatches to the exact same
`capability_index.invoke_capability` choke point the inline path uses -- one
execution primitive, one enablement gate, shared by both. Every state
transition (`queued`/`started`/`completed`/`failed`) is already a trace event
for free, via the existing AST-066 task state machine (§12.3) -- this task
adds no new tracing for the task lifecycle itself. No resolver is registered
for this kind: every `capability-invoke` task runs entirely in-process and
never carries an `external_job_id`, so a row still `started`/`progress` at
engine restart is genuinely unreconcilable and correctly becomes `orphaned`
via the existing restart-reconciliation logic (§12.4) -- the same outcome a
kind with no resolver already produces.

The actual task-completion announce/artifact-open path (§12.5, AST-066/069/
070) is pre-existing infrastructure this task does not extend or modify.

### 7. Tracing (§10.1/§10.6)

New event kinds, all inside the enumerated `skill.*` namespace:

- `skill.request` -- one per parsed directive. `status: "parsed"` for the
  one the turn acts on, `status: "ignored"` for any extra (§1).
- `skill.invoke` -- one `status: "start"` / `status: "ok"` pair per actual
  invocation attempt, sharing a `span_id`, `parent_span_id` = the turn's
  `turn_id`.
- `skill.error` -- first-class for every non-invocation refusal reason:
  `invalid_directive` (malformed JSON / missing name / an unterminated
  fence), `unprovisioned`, `invalid_params`, `disabled` (a defense-in-depth
  race guard -- `invoke_capability` itself still enforces §17.2), `timeout`,
  `queue_full`, `reload_failed`, `followup_failed` (round-1 review finding
  4: the same-turn follow-up completion itself raised), `internal_exception`
  (round-1 review finding 8: the outer hook guard caught something
  unexpected), and any other `adapters.AdapterError`.
- `skill.gap` -- the pre-existing #346 event, now also carrying
  `requested_name` in its payload (§4).

Every event above carries `turn_id`; `skill.invoke`/`skill.error` for an
in-flight invocation also carry `span_id`/`parent_span_id` for waterfall
correlation.

## Decisions (recorded so a future reader does not re-derive them)

- **Resolution is name-based, not the pre-existing roster/nearest scoring
  reused as-is.** `roster_for_turn`/`nearest_entries` protect passive roster
  injection and refusal display respectively; neither is the right tool for
  "does the capability I was explicitly told to invoke exist." A new,
  narrow, `_score`-independent function (`resolve_by_name`) keeps those two
  functions' existing contracts completely unchanged.
- **No new parameter-validation call site.** `invoke_argv`/`invoke_mcp`
  already validate-before-spawn; engine.py catches their
  `ParamValidationError` rather than pre-validating a second time. One
  validation path stays the single source of truth for what "valid params"
  means (matches ast-E6.md's own "one argv-validation path, two invoke
  flavors" decision).
- **`capability_gap_reply`'s `requested_name` is additive, not a new
  function.** The brief's own framing ("call the EXISTING
  `_capability_gap_check`/`capability_gap_reply` machinery... with the
  request excerpt") is implemented literally: one optional keyword parameter
  threading a stronger signal through the SAME function and the SAME
  rendering helpers (`_render_capability_gap_refusal`,
  `_draft_capability_acquire_offer`), rather than a parallel sibling that
  would fork the refusal-shape logic in two places.
- **Inline invocation timeout is a bare module constant
  (`engine.CAPABILITY_INVOKE_TIMEOUT_SECONDS`), not a new config surface.**
  Keeps this task's scope to "no new provider flags" (non-scope) while still
  giving tests a monkeypatchable seam, matching this codebase's existing
  house pattern for exactly this kind of knob.
- **`longRunning` is a bool marker, not a duration or a queue-priority
  hint.** The simplest possible reading of "declares itself async" (design
  point 3's own phrasing) -- a capability author says "this will not finish
  inline," nothing more; how long it actually takes is not this mechanism's
  concern (the task queue has no deadline of its own, §12.3).
- **The directive fence language tag is `capability`, chosen to be
  self-describing and collision-unlikely** against a model's own use of
  fenced code blocks for actual code (which almost always carry a real
  language tag like `python`/`bash`/`json`, never the literal word
  `capability`).
- **A failed follow-up degrades to a template, never a raw error (round-1
  review, finding 4/5).** The alternative -- letting the failure propagate,
  or returning an empty reply -- is strictly worse once the capability has
  already run: the user learns nothing about an action that genuinely
  happened, and a client that retries on a 502/empty-looking reply risks
  re-running it. A rougher, templated reply that honestly states the result
  is the safer failure mode.
- **Usage is aggregated across both completions, never replaced (round-1
  review, LOW finding 7).** `turns._merge_usage` sums numeric fields present
  on both sides of a hook-driven follow-up completion; a hook that never
  drives a second completion (a refusal, a validation error) leaves the
  first completion's own usage completely untouched -- the merge only ever
  engages when a REAL second adapter call happened.
- **The queued-capability timeout is a second, independent module constant,
  not a parameter threaded through the same one.** Two call sites sharing
  one constant is exactly how the HIGH finding 1 bug happened in the first
  place; keeping `CAPABILITY_INVOKE_TIMEOUT_SECONDS` (inline) and
  `CAPABILITY_TASK_TIMEOUT_SECONDS` (queued) as two clearly-named,
  independently-documented constants makes it structurally obvious which
  one governs which path.

## §17 invariants -- unaffected, verified

- Invariant 2/3 (disabled never invoked; argv-array, schema-validated,
  no shell): unchanged -- this task's invocation paths (both inline and
  queued) go through the EXISTING `invoke_capability` choke point, which
  already enforces both.
- Invariant 5 (atomic, serialized brain writes): unaffected -- the gap
  flow's plan-note draft still only ever reaches the distiller queue via
  `_enqueue_gap_note`, exactly as #346 shipped it.
- Invariant 7 (turns never block on the distiller/index/task queue): holds
  -- the bounded inline invoke is the turn's OWN explicitly-requested,
  time-boxed action, not background work being awaited; a longRunning
  capability is enqueued, never awaited, and the turn replies immediately.
  `on_reply`'s second `complete_fn` call is likewise part of the SAME turn's
  own synchronous work, not a queue wait.
- Invariant 11 (a task executor never adopts a caller-supplied artifact
  path): unaffected -- `run_capability_invoke_task` never touches
  `artifact_path` at all; its `{"result": ...}` return shape carries no
  path-shaped field for `tasks._process_create` to persist as one.

## Round-2 review: two final findings

- **NEW-MEDIUM -- the trailing-element rule was enforced but never
  taught.** Round-1's `actionable` policy (§1) is correct, but the roster
  teaching text never told the model about it -- an ordinary "Let me
  check...\n\n`​```capability...`​``\n\nOne moment!" reply now silently did
  nothing (the directive is present but not actionable, per the trailing
  rule) while the VISIBLE text still told the user an action was underway,
  a confusing silent no-op. `_CAPABILITY_DIRECTIVE_TEACHING_LINES` now
  states explicitly: "The block must be the LAST thing in your reply --
  put any explanation BEFORE it, never after: if you say anything more
  once the block ends, it will not be treated as a real request." This
  does not change the enforcement itself, only makes the model aware of
  the rule it is already held to.
- **NEW-LOW -- the dangling-fence detector's word-boundary false-
  positived on any unrelated tag merely STARTING WITH "capability".**
  `_CAPABILITY_DANGLING_OPEN_RE`'s original `\b.*\Z` suffix matched a bare
  word/non-word transition -- satisfied immediately after "capability" by
  EITHER a hyphen (` ```capability-notes `) or a period (` ```capability.md
  `), both non-word characters. Since this detector only ever runs on text
  that already had every COMPLETE, well-formed pair stripped out, matching
  here means "delete everything from this point to end-of-string, report
  an error" -- so an entirely unrelated, well-formed fenced block (e.g. a
  reply that legitimately includes a `​```capability-notes` code sample)
  had its real content (and everything after it) silently destroyed, plus
  a spurious `invalid_directive` trace. Fixed by requiring "capability" to
  be the COMPLETE tag on its own line (`[ \t]*$` -- only trailing
  spaces/tabs allowed before the line ends), the SAME discipline the
  opening-fence regex already applies; a genuinely dangling directive
  (nothing else on that line) still matches exactly as before.
- **Optional nit taken: the unreachable "could not understand" fallback
  removed from the non-actionable branch.** `engine.py`'s hook returned
  `visible_text or "I could not understand that capability request."` when
  a valid-but-non-trailing directive was found -- but `visible_text` can
  never be empty in that branch by construction (a valid directive only
  fails the trailing check when genuine, non-whitespace prose follows it,
  and that prose IS what `visible_text` carries), so the fallback was dead
  code with a wrong-anyway message (the directive WAS understood, it was
  just correctly not honored). Removed; `visible_text` alone is returned.
- **Optional nit taken: the "never shown to the user" promise (§1)
  narrowed to the exact fence syntax.** An indented (4-space) code block,
  or one using 4+ backticks instead of exactly 3, is not recognized as a
  directive at all and renders verbatim if a model ever produces one --
  documented as a scope boundary, not a gap this task closes.
