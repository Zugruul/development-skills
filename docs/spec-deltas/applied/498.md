## §12.4 — EXTENDED (reconciliation is guarded by a per-root owner heartbeat, AST-067's retro-review F2, issue #485)

**Section extended**: §12.4's reconciliation contract (startup sweep + AST-070's periodic
live twin, both narrowed to assistant candidates by #497) implicitly assumed each engine
process reconciling a root was the ONLY live engine that could ever be working that root's
queue. On a machine running multiple neural-view engines with overlapping scan bases (the
same repo anchored under more than one engine's configured base directory — a routine
setup on the reporting machine), that assumption is false: a SECOND engine's startup sweep,
or its periodic live pass, has no way to tell "crash leftover" apart from "another engine's
live in-flight row" — it would orphan (or, for the periodic sweep, resolve/complete) rows a
FIRST engine is actively draining, purely because reconciliation had no concept of who else
might be alive. This was latent until AST-070's harness-job executor gave rows a realistic
in-flight lifetime; it is real now.

**Contract now**: `tasks.sqlite` (the SAME per-root db §12.3 already defines — no new file,
no cross-repo state) gains a single-row `task_owner` table: `engine_id` (a `uuid4().hex`
generated once per engine process, unless the caller supplies its own), `pid`, `host`
(`socket.gethostname()`), `heartbeat_at`. Both reconciliation sweeps now skip a candidate
root entirely (never touching its task rows this pass) when ALL of:

- a `task_owner` row exists,
- its `engine_id` is **not** this engine's own, and
- its `heartbeat_at` is within the staleness window (below).

Any other case — no owner row at all (the pre-#498 default; every existing reconciliation
test fixture creates none, so absent-owner behaves exactly as before this task), the
engine's **own** id (an engine's in-flight work must never wedge on its own possibly-stale
heartbeat), or a heartbeat older than the staleness window (the owning engine crashed) —
falls straight through to the existing §12.4 reconciliation logic, unchanged.

**Claim discipline (narrow, deliberately)**: ownership is claimed ONLY by actually draining
a root — `_process_create` handling one queued item through to its executor. Neither sweep
ever claims ownership of a root it is merely scanning, including a root it finds something
to reconcile in: a periodic reconciler that claimed ownership by the act of looking would
let a purely-scanning engine falsely present itself as "the live engine" for a root nothing
is actually routing real work to.

**Refresh discipline (round-1 review MAJOR-1, corrected)**: the FIRST version of this delta
claimed a periodic-tick refresh alone was sufficient to keep a between-drains root warm —
review round 1 reproduced the actual failure: `_process_create` calls an executor
SYNCHRONOUSLY on the single worker thread (§12.3's execution model), so the main loop's own
tick (and the periodic live-reconcile pass it drives) literally cannot run while that call
is in progress. At production defaults, a 300s harness job was measured stale ~70% of its
life against the 90s window before this fix — the heartbeat was never being refreshed AT
ALL for the executor's entire duration, not merely refreshed too infrequently. The corrected
design refreshes from THREE places:

1. **On every drained item** (`_process_create`'s own claim) — unconditional, best-effort.
2. **From `report_progress`** (round-1 review MAJOR-1(a)) — an executor that reports
   progress (harness.py: ~every 2s) is the cheapest available "still genuinely alive"
   signal, on the SAME thread and connection `_process_create` already holds. Rate-limited
   to no more than once per `owner_stale_seconds / OWNER_STALE_MULTIPLIER` (i.e. "~window/3",
   the SAME cadence the periodic tick uses by construction when `owner_stale_seconds` is
   left at its default derivation) so a tight progress-reporting loop never hammers sqlite.
3. **A background heartbeat-timer thread** (round-1 review MAJOR-1(b)) — started once per
   `run_worker` call (only while `repos_getter` is given), waking every effective tick
   interval to refresh every root this engine currently owns, INDEPENDENT of whether the
   main thread is free. This is the fix for (1) and (2) both being executor-dependent: an
   executor that never calls `report_progress` at all (issue #508's own capability-invoke
   executor is the concrete example already in this codebase) would otherwise still freeze
   the heartbeat for its whole run. Considered making that executor call `report_progress`
   periodically instead — rejected: it would fix only that one, KNOWN executor, leaving the
   same gap open for any future task kind that also doesn't call it. The timer thread is
   executor-agnostic and closes the gap structurally, not by convention.

   The timer thread never touches `run_worker`'s own long-lived `conns[root]` connections
   (Sec10.2's single-writer-PER-THREAD discipline: a `sqlite3.Connection` object must never
   be used from a thread other than the one that created it) — it opens its OWN short-lived
   connection per root per wake, mirroring `list_tasks`'s existing "fresh, short-lived
   connection per call" precedent, just for a write instead of a read. Joined (bounded) in
   `run_worker`'s `finally`, before this engine's owner rows are released (below), so no
   refresh can race the shutdown handoff.

   `owned` (the set of roots this engine has ever drained) moved from a bare `set()` to a
   small lock-guarded wrapper (`_OwnedRoots`) once a second thread started reading it
   concurrently with the main thread's own adds/discards — a bare set is not safe for that.

**Ownership honest about its writers (round-1 review, delta wording fix)**: §10.2's
single-writer discipline for the `tasks` table itself is unchanged — only one thread, in at
most one live engine, ever writes a `tasks` row for a given root at a time. `task_owner` is
different and new: it is written by up to three actors now — the main worker thread (on
drain and on its own tick), the background heartbeat-timer thread (a SEPARATE connection,
same process), and potentially a DIFFERENT engine PROCESS entirely. All three are
serialized the same way: WAL + `busy_timeout` (already pragma'd by `_open_conn`), never an
application-level lock. This is the first table in this file genuinely designed for
concurrent writers by more than one connection.

**Wall-clock, not monotonic, and why**: `heartbeat_at` is `datetime.now(timezone.utc)`, a
real-time (wall-clock) timestamp — deliberately, not `time.monotonic()`. Ownership must be
read and compared ACROSS processes (a different engine's sweep reading another engine's
`task_owner` row) and across restarts; a monotonic clock's epoch is arbitrary per-process
and carries no meaning once you cross a process boundary, so wall-clock is the only choice
that lets staleness be computed by anyone who reads the row. Known, documented gap (same
posture as `harness.py`'s own DOCUMENTED GAP sections): a wall clock can step — an NTP
correction moving the clock backward could make a genuinely fresh heartbeat look
momentarily stale (safe direction: extra, spurious reconciliation contention, never a
wedge), while a large forward step could make a stale heartbeat look briefly fresh (self-
correcting once real time catches up; MAJOR-2(a)'s same-host dead-pid check is immune to
this entirely, since it never consults the timestamp).

**Same-host dead-pid recovery (round-1 review MAJOR-2(a))**: `pid`/`host` were being
written into `task_owner` but never read — a fast restart on the SAME host inherits a
predecessor's heartbeat that is still timestamp-fresh (the predecessor only just died),
which would otherwise wedge the root until the staleness window elapses on its own (or,
absent MAJOR-2(b) below, for a `queued`/no-`external_job_id` row, effectively forever).
`_owner_blocks_reconciliation` now checks, BEFORE and regardless of heartbeat age: if
`owner.host == socket.gethostname()` and `not _pid_alive(owner.pid)` (mirroring
`harness._pid_alive`'s `os.kill(pid, 0)` signal-probe exactly, duplicated rather than
imported to avoid a circular `tasks` <-> `harness` dependency), the owner is dead RIGHT NOW
and reconciliation proceeds instantly. A foreign host's pid is never checked this way (no
portable, safe way to ask a different machine "is this pid alive") — only the age-based
staleness window governs cross-host recovery.

**Deferred startup-class retry (round-1 review MAJOR-2(b))**: the one-time startup sweep
(§12.4's own documented shape) is the ONLY path that ever reconciles a bare `queued` row or
a `started` row with no `external_job_id` (the periodic live pass deliberately narrows to a
`started`/`progress` + `external_job_id`-only subset — see `_LIVE_RECONCILE_TARGET_STATES`).
A root the startup sweep skipped for ownership at that one moment would previously never
get another startup-class pass for the rest of the process's life — round-1 review
reproduced this exactly: those two row shapes stayed wedged even after the foreign owner
went stale. Fixed with `pending_startup_reconcile`, an in-memory set: every root
`_reconcile_all` skips for ownership (not for #497's own candidate-scoping, which has
nothing to defer) is recorded into it; `run_worker`'s periodic tick
(`_retry_pending_startup_reconcile`) re-checks ownership on each tick for every pending
root, and once it no longer blocks, runs the FULL `_reconcile_root` (never
`_reconcile_live_root` — the whole point is recovering the wider row set the live pass
never covers) and stops retrying that root.

**Staleness window**: `owner_stale_seconds`, default `OWNER_STALE_MULTIPLIER` (3) times the
effective live-reconcile interval (the configured `live_reconcile_interval`, or the default
30s if periodic reconciliation is disabled for that call). 3x is the same reasoning a TCP
keepalive or a Kubernetes liveness-probe failure threshold uses: one missed tick is ordinary
jitter (a GC pause, a slow `fsync` under WAL contention), not evidence of a crash, and must
never let a live owner's in-flight rows get snatched by a competing engine's sweep over a
single missed beat; three consecutive misses is no longer plausibly transient. This also
bounds how long a genuine crash can wedge a root's rows to a small, known, explainable
multiple of the tick interval (90s at defaults) — never forever, preserving §12.4's own
crash-recovery invariant (and, since MAJOR-2(b), genuinely true for EVERY row shape, not
just the ones the periodic pass alone can reach).

**Cross-config caveat**: `owner_stale_seconds` and `live_reconcile_interval` are independent
keyword arguments — a caller CAN override one without the other (this module's own tests do,
deliberately, to keep test wall-clock time short). Decoupling them in a REAL deployment is
not recommended without a reason: the report_progress rate limit and the background timer
both derive their refresh cadence from the effective tick interval, so an
`owner_stale_seconds` set noticeably SHORTER than a few multiples of `live_reconcile_interval`
risks a live, healthy owner's heartbeat reading as stale between refreshes — the default
derivation (`owner_stale_seconds` always exactly `OWNER_STALE_MULTIPLIER` x the effective
interval) is the only combination this task has verified never does that.

**Idle-owner pruning (round-1 review advisory (a))**: without this, an engine that drained a
root exactly once would keep refreshing its heartbeat for as long as the PROCESS stays
alive — both refresh paths iterate `owned` unconditionally — blocking every OTHER engine's
reconciliation of that root forever, even with nothing left to protect (compounding
MAJOR-2's wedge risk the same way a never-expiring lock would). `_maybe_prune_owned_root`
runs after every drained item finishes (success or failure): if the root has no
`queued`/`started`/`progress` rows left at all, it is dropped from `owned`. No explicit
on-disk change — the existing `task_owner` row is left exactly as it was and simply ages out
of the staleness window on its own, indistinguishable to another engine from a crashed
owner's. Ownership is reclaimed automatically the moment this engine drains that root again.
Cross-engine caveat (round-2 review): if this engine keeps intermittently draining the SAME
root (prune when idle, re-claim on the next item) right as a DIFFERENT engine's sweep is
mid-tick against it, ownership can briefly "flap" between pruned and re-claimed. Safe
direction only — at worst a redundant reconciliation attempt on a row that has already
moved to a terminal state, which `_reconcile_row`'s own candidate-state `SELECT` already
excludes (a terminal row is not a member of `_RECONCILE_TARGET_STATES`/
`_LIVE_RECONCILE_TARGET_STATES` to begin with), never a real ownership conflict or data
corruption — self-correcting the next time either engine reads a settled `task_owner` row.

**Instant shutdown handoff (round-1 review advisory (b))**: `run_worker`'s `finally` now
deletes THIS engine's `task_owner` row (`WHERE id = 1 AND engine_id = ?`) for every root it
held a connection for, before closing. A graceful `stop()` is not a crash — there is no
reason to make a legitimate successor (e.g. the same repo re-routed to a different engine)
wait out the staleness window when the departing engine can just say so on its way out.

Round-2 review (shutdown race): the heartbeat-timer thread (MAJOR-1(b)) is joined BEFORE
this deletion runs, but a single in-flight `_claim_ownership` can legitimately block up to
`busy_timeout` (5s, `_open_conn`'s own pragma) waiting for a lock — longer than a short
bounded join alone would wait. A bounded join that times out while that write is still in
flight would let the timer thread land it AFTER the deletion, resurrecting this engine's own
row right after handing it off — exactly backwards. The join is now two-stage: a bounded
attempt first (the fast path — nothing contended, exits promptly), then, only if the thread
is still alive, an UNCONDITIONAL fallback join with no timeout. This is what actually
guarantees no write can ever land after the delete (a structural proof, not a probability) —
and it can never hang forever either, since sqlite's own `busy_timeout` already bounds how
long any single claim can possibly block.

**Normal-skip visibility (round-1 review advisory (c))**: a genuine, working ownership skip
(the common case, not a bug) now also emits its own `task.ownership_skip` trace event
(payload: `root`, `owner_engine_id`, `heartbeat_at`) — previously only the FAILURE path
(`task.ownership_check_failed`) was traced at all, leaving "skipped because another engine
legitimately owns this" and "root has nothing to reconcile" indistinguishable from the
trace stream alone. Round-2 review (dedup): `_retry_pending_startup_reconcile`'s own
ownership check passes `traces_queue=None` — every root it ever tracks came from
`_reconcile_all`'s pass over the SAME `repos_getter()` list `_reconcile_live_all` re-walks
every tick, so a still-candidate deferred root is, by construction, ALSO re-checked (and
already traced, if still blocked) by `_reconcile_live_all` on the identical tick; without
this, the same skip decision for the same root in the same tick would trace twice.

**Failure honesty**: a `task_owner` read failure (locked, corrupt, mid-migration) skips the
root for that pass — fail CLOSED, treated the same as "a live foreign owner was found" —
and is never silent: a `task.ownership_check_failed` trace event (payload: `root`, `error`)
plus a stderr line record why, so a failure that could otherwise look indistinguishable from
"nothing to reconcile" always leaves a trail. This is a deliberate asymmetry with the
unparsable-timestamp case (round-1 review MINOR-1: a `heartbeat_at` that fails to parse, OR
whose age subtraction raises — a NAIVE, tzinfo-less timestamp parses fine but then raises
`TypeError` subtracting it from an aware `datetime.now(timezone.utc)`, which used to escape
this function's `try` entirely and get mis-treated by the CALLER's generic per-root handler
as an unrelated failure, an untraced fail-CLOSED contradicting this exact contract — both
the parse AND the subtraction are inside the same `try` now) falls through to normal
reconciliation, fail OPEN: a read that raises tells this engine nothing at all about whether
a live owner exists, while a row that exists but has an unusable timestamp still proves
*something* was claimed and is at minimum decodable as "not usefully fresh".

**Connection safety on a failed claim (round-1 review MINOR-2)**: `_claim_ownership` now
defensively rolls back BEFORE its own `BEGIN IMMEDIATE` (mirrors `_transition_safe`'s same
posture) and rolls back again, then re-raises, if its own upsert fails — a failed claim used
to leave the connection mid-transaction, poisoning the NEXT `_insert`/`_transition` on that
root with "cannot start a transaction within a transaction", the exact failure mode
`_transition_safe` already exists to prevent for the `tasks` table's own transitions.

**Unaffected**: §12.3's queue/state-machine contract, §12.4's own per-row re-poll/orphan
logic (`_reconcile_row`), and #497's candidate-with-an-existing-db scoping are all
unchanged — this delta only adds a gate BEFORE either sweep calls into that unchanged
per-row logic, never touching how a root gets there or what happens once it's not skipped.
`run_worker` gains two new, backward-compatible keyword arguments (`engine_id=None`,
`owner_stale_seconds=None`, both defaulted as described above) — every existing caller/test
that constructs the worker without them is unaffected, matching every other opt-in
convention (`repos_getter=None`, `traces_queue=None`) this module already established.

### Not addressed by this task

Issue #507 (a resolver-less-kind orphaning rows in the live pass) is a separate, pre-
existing gap in `_reconcile_live_root`'s candidate-row selection, orthogonal to ownership —
this task does not resolve it and does not make it worse: the ownership gate runs strictly
before the per-row reconciliation logic #507 concerns, for every row regardless of kind.
