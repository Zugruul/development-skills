## §7.2 — ADDITIVE (chat overlay header names the model, issue #492)

**Section unchanged, extended**: §7.2 already requires the voice panel header
to show the sole selected assistant's main name ("VOICE · JARVIS"). #492
extends the SAME "name a selected assistant beside its label" idea to the
**chat overlay's** header, and to the model the assistant is actually
running on, not just the assistant's own name.

**`GET /assistant/status` contract, extended**: each entry in `candidates`
now carries a resolved `llm` sub-mapping alongside `name`/`aliases`/`root`:

```
candidates: [
  {name, aliases, root, llm: {provider: str|None, model: str|None}},
  ...
]
```

`llm.provider`/`llm.model` mirror the candidate's own `assistant:` section
(`section["llm"]["provider"]`/`["model"]`) verbatim — the model id is never
shortened or reformatted (repo invariant: model names render verbatim, e.g.
`claude-sonnet-5`, never a shorthand). `engine.py`'s `_candidate_llm`
resolves this defensively: a missing `llm` key, an `llm` value that is not
a mapping, or a non-string `provider`/`model` each degrade that field (or
both) to `None` rather than raising — in practice every `discovery.scan`
"candidate" already passed `assistant.config.validate_assistant`, which
requires `llm.provider`/`llm.model` to be strings, so this is a
defense-in-depth path, not a reachable production gap.

Carrying `llm` on every candidate (not just the selected one) means the
chat overlay page can resolve the selected assistant's model **locally**
off the list it already has cached (`window.__assistantCandidates`),
including across a #485 tab switch, without a second round-trip to the
server.

**Chat overlay header, extended**: the header's assistant-name element
(`#ast-chat-assistant-name`) gains a sibling, muted model element
(`#ast-chat-assistant-model`, `.ast-chat-assistant-model` — same
`var(--muted)` idiom other quiet meta text in the page uses, e.g.
`.ast-chat-lastx-label`/`.ast-chat-chips`), positioned in the header after
the tab row. Rendered as `"· <model>"` (no leading space — the header's
flex `gap` already supplies the separation), e.g. `MEGABRAIN · claude-sonnet-5`.

Rules (mirroring the name element's own existing empty-when-unknown
posture):
- The separator + model render ONLY when BOTH a selected assistant AND its
  model id are known — never a bare `"· "`, never `"· undefined"`.
- Resolved through one shared helper, `assistantModelSuffix(name)`, off
  `window.__assistantCandidates` (Array.isArray-guarded — a missing or
  malformed cache degrades to `""` rather than throwing). Every surface
  that can change or refresh the active assistant calls it and writes the
  result to `#ast-chat-assistant-model`, so the model can never drift out
  of step with the name it labels:
  - `openChatOverlay`'s status fetch (initial open).
  - `switchAssistantTo` (review round 1, finding 2), immediately after it
    adopts the server's echoed selection — this is what the chat tabs and
    the voice-header switch dropdown both call, so a tab click or a
    dropdown switch updates the header synchronously instead of waiting on
    the next poll tick.
  - The #485 keep-in-step poll (`startChatStatusSync`), on **every** tick
    (review round 1, finding 3) — not only a tick where `selected` changes.
    A human editing `llm.model` in `project.yaml` (which `_status`
    re-scans live) changes the model without changing who's selected, and
    the model must still catch up within one poll interval.
- Stays VISIBLE when `renderChatAssistantTabs` hides the name element (2+
  candidates — review round 1, finding 1 (BLOCKER)): tabs answer "who am I
  talking to", but the model is a different fact tabs never carry, so on
  any machine with 2+ discovered assistants the model still renders next
  to the tab row instead of disappearing along with the name.
- Gated (Skip) or `outcome: "none"`: stays empty, exactly as the name does
  today (both are driven by the same `status.selected`, which is `None` in
  both those states).
